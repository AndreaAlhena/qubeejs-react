Server rendering comes in two kinds, and the adapter's part differs between them.

## Client components rendered on the server

Server-side rendering turns your client components into HTML once, then hydrates them in the
browser. The adapter's hooks support it through the server snapshot of `useSyncExternalStore`:

- **`useQubee`, and `useQubeeContext` under `<QubeeProvider>` with a configuration**, get a fresh
  instance per tree. It renders its initial state on the server and hydrates to the same state — no
  mismatch.
- **`<QubeeProvider value={qubee}>`** hands the instance to you, so its lifetime is yours: create it
  per tree or per request, never as a module-level instance shared across server requests, and
  configure it the same way on both sides. A client-only write before hydration (from
  `localStorage`, say) makes the client's snapshot differ from the server HTML; make such writes in
  an effect.
- **`useBrowserAdapter`** knows no URL on the server, so a list that uses it renders its defaults
  there, and its real state right after hydrating. To render the right page on the server, use a
  router that knows the URL there — your framework's.

## React Server Components

A Server Component never calls the hooks of `@qubeejs/react`: hooks and context exist only in
client components. For its own work it imports `@qubeejs/core`, which never imports React — and the
core has everything a server needs to read the URL, fetch the page and link onward:

- `readListState` takes Next's `searchParams` record as it is.
- `fetchPage` returns `toPlain()`, a plain object — the only kind a Server Component can hand to a
  Client Component.
- `buildListHref` gives server-rendered links the same URL rules as the client: defaults left out,
  the page reset, foreign parameters kept.

When the search changes, the router navigates, Next renders the Server Component again with the new
`searchParams`, and the client component receives the new page as props. `isPending` stays `true`
until it has arrived. `useNextListRouter` is the small adapter you write yourself, on
[Vite / Next.js / React Router](/introduction/frameworks/).

This page reads `searchParams` on the server, which makes the route dynamic: it renders on each
request, so `useSearchParams` in the router adapter needs no `<Suspense>` boundary. A statically
rendered route that calls `useSearchParams` does need one above it, or `next build` fails.

:::caution[Bee aware]
Declare the list — `articleList` — in a module both sides import. It holds functions, so it can never
travel from a Server Component to a Client Component as a prop.
:::

## A Next.js adapter

A Next.js adapter is planned as an entry point of this package, `@qubeejs/react/next`, not as a
package of its own. It will ship the router adapter that replaces the `useNextListRouter` above.
Until then, this page is the whole integration.
