The adapter for TanStack Router is an entry point of its own, `@qubeejs/react/tanstack-router`. It
needs TanStack Router 1.49 or later, the first release whose `navigate` takes an href.

```sh
npm install @qubeejs/react @qubeejs/core @tanstack/react-router
```

## Keep the query as typed

TanStack Router owns the query string: it parses it into a search object and writes that object
back on every navigation. Its default serialisers read each value as JSON, so the URL a list asks
for is not always the URL it gets:

| The user types  | TanStack Router writes |
| --------------- | ---------------------- |
| `10 ` (a space) | `10`                   |
| `"react hooks"` | `react hooks`          |
| `1.50`          | `1.5`                  |
| `1e3`           | `1000`                 |

The list settles on what the router wrote — the URL always wins — so a search box loses those
characters when its debounce lands: `10 years`, typed with a pause after the space, ends up as
`10years`.

If the app has a free-text search, give the router the two serialisers the entry ships, which
keep text as text:

<Code code={tanStackRouter} lang="tsx" title="src/router.tsx" />

[`parseSearch`](/api/tanstack-router/parse-search/) reads every value as the string it is in the
URL, and a repeated name as a list; [`stringifySearch`](/api/tanstack-router/stringify-search/)
writes it back. With them, every search value in the app is a string, or a list of strings: a
route whose `validateSearch` wants a number has to coerce it. TanStack Router's guide to
[custom search param serialization](https://tanstack.com/router/latest/docs/framework/react/guide/custom-search-param-serialization)
covers the alternatives.

## A list page

The links are real anchors with a plain-click handler, as in the
[Pagination bar](/recipes/pagination-bar/). Under a `basepath`, `list.href(…)` is the path inside
it — TanStack strips the basepath from the location's pathname — so give the anchor
`router.buildLocation({ href: list.href(…) }).publicHref`, which adds the basepath back.

## How it works

- It reads `location.searchStr` — the query string as TanStack Router serialised it — and
  `location.pathname`.
- It navigates with `router.navigate({ href })`, which takes a fully built href and applies the
  router's basepath and rewrites, so the list's URL rules — defaults left out, foreign parameters
  kept — apply unchanged. The router's search serialisers still run on that href, as above.
- A list navigation keeps the scroll position: TanStack Router would otherwise scroll to the top
  on every sort, page or search. `<TanStackRouterAdapter scroll>` — or
  `useTanStackRouterAdapter({ scroll: true })` — hands the scrolling back to the router.
- If the route declares `validateSearch`, let it pass the list's keys through untouched: a validator
  that drops unknown keys drops the list's.
- For the one list that should not follow the provider, pass `useTanStackRouterAdapter()` to the
  hook — see [Adapters & providers](/guide/adapters/).
